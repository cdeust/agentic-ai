6. Contrat de plugin (manifeste)

Le manifeste est la seule chose que la gateway lit. Il génère le module importable, le catalogue de repli, la politique de routage et les limites. Un plugin sans manifeste valide n'est pas routé.

name: memory-recall
version: 1.2.0
domain: memory
owner: cortex
transport: http            # MCP léger exposé au gateway
tools:
  - name: recall
    description: Rappel typé, filtré en SQL, rerank par Judge
    input_schema: ./schemas/recall.in.json
    output_schema: ./schemas/recall.out.json
    kind: data              # data | agent | workflow
    max_result_tokens: 600
    latency_budget_ms: 200
    validator: schema       # schema | verify | spec-lint | none
containers: []              # aucun pour un data tool
writes_tables: []           # lecture seule
reads_domains: [memory]
calls_allowed: [judge]      # DAG : ce que ce plugin peut appeler
egress: none
model_min: none             # none | local | haiku | sonnet | opus

name: codebase-ask
version: 0.3.0
domain: code
owner: ai-architect-mcp-codebase
tools:
  - name: ask
    kind: agent
    max_result_tokens: 1000
    validator: citations     # chaque fichier:ligne existe et contient le texte cité
containers:
  - profile: scout
    mounts: [repo:ro]
    egress: none
    model_min: sonnet
    budget_tokens: 40000
writes_tables: []
reads_domains: [code, memory]
calls_allowed: [code-index, memory-recall]

Règles appliquées par la gateway à partir du manifeste : un tool data n'a pas de conteneur ; un tool agent crée une task ; writes_tables doit être disjoint entre tous les manifestes (un écrivain par table) ; calls_allowed doit former un graphe acyclique ; egress autre que none impose une écriture en quarantaine.

7. CI avec claude-code-action

Principe : le runner est un client MCP de la gateway, rien d'autre. Il n'exécute pas de code produit par un agent, il ne porte aucune clé Anthropic statique, et il ne voit que trois tools. Tout ce qui demande un conteneur a lieu dans la plateforme.

7.1 Ce que l'action fournit, vérifié dans sa documentation

  • MCP : claude_args accepte --mcp-config (fichier ou JSON inline, plusieurs flags fusionnés) et --allowedTools. Les serveurs ajoutés fusionnent avec les serveurs GitHub intégrés de l'action.
  • Plugins : inputs plugins et plugin_marketplaces, listes séparées par retour à la ligne.
  • Auth sans clé : anthropic_federation_rule_id, anthropic_organization_id, anthropic_service_account_id (optionnel anthropic_workspace_id). Ce sont des identifiants, pas des secrets ; ils peuvent vivre dans le fichier de workflow. Le job doit avoir id-token: write. Ne pas mettre anthropic_api_key en parallèle, la clé statique prendrait le pas.
  • Modes : détection automatique. Mention @claude → mode tag ; événement PR ou issue avec prompt → automation. track_progress force le mode tag avec commentaire de suivi. L'input mode est déprécié.
  • Isolation du runner : scrub des secrets dans les sous-processus et PID namespace via bubblewrap sur runners Linux (variable CLAUDE_CODE_SUBPROCESS_ENV_SCRUB). La doc précise que cela réduit le risque d'injection sans l'éliminer, d'où la règle « le runner n'exécute pas ».
  • Garde-fou : agent-approval-check impose des approbations humaines sur les PR contenant des commits d'agent ; à déclarer en status check obligatoire. Le workflow s'exécute depuis la branche par défaut, une PR ne peut pas le modifier pour s'auto-approuver.
  • Limite : le token GitHub de l'app est limité au dépôt courant. Pour la CI de platform qui touche plusieurs dépôts, c'est le runner qui clone, pas Claude.

7.2 claude-review.yml, revue de PR via la gateway

name: claude-review
on:
  pull_request:
    types: [opened, synchronize, ready_for_review, reopened]

jobs:
  review:
    runs-on: [self-hosted, platform]       # runner dans le même segment réseau que la gateway
    permissions:
      contents: read
      pull-requests: write
      id-token: write                      # federation OIDC
      actions: read
    steps:
      - uses: actions/checkout@v6
        with: { fetch-depth: 1 }

      - name: MCP config vers la gateway
        run: |
          cat > /tmp/mcp.json << EOF
          {"mcpServers": {"gateway": {"type": "http",
            "url": "https://gateway.internal/mcp",
            "headers": {"Authorization": "Bearer ${{ secrets.GATEWAY_CI_TOKEN }}"}}}}
          EOF

      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_federation_rule_id: fdrl_xxxxxxxx
          anthropic_organization_id: 00000000-0000-0000-0000-000000000000
          anthropic_service_account_id: svac_xxxxxxxx
          plugin_marketplaces: https://github.com/cdeust/marketplace.git
          plugins: |
            ai-architect-standards@cdeust
          track_progress: true
          use_sticky_comment: true
          prompt: |
            REPO: ${{ github.repository }}
            PR: ${{ github.event.pull_request.number }}
            Revue selon les standards ai-architect.tools.
            Utilise uniquement la gateway : execute un script qui importe code et memory,
            appelle code.verify sur le diff, puis codebase.ask pour le contexte.
            Toute affirmation cite fichier:ligne. Aucun fichier n'est exécuté sur ce runner.
          claude_args: |
            --mcp-config /tmp/mcp.json
            --allowedTools mcp__gateway__search,mcp__gateway__describe,mcp__gateway__execute
            --max-turns 15

Le jeton GATEWAY_CI_TOKEN est un client credential émis par la gateway pour le profil ci-review, limité aux modules code-index, verify, codebase-ask, memory-recall. C'est le seul secret du workflow, et il n'ouvre rien d'autre que ces quatre modules.

7.4 issue-to-spec.yml, étape du pipeline exigences → PRD

name: issue-to-spec
on:
  issues: { types: [labeled] }

jobs:
  spec:
    if: github.event.label.name == 'spec'
    runs-on: [self-hosted, platform]
    permissions: { contents: write, pull-requests: write, issues: write, id-token: write }
    steps:
      - uses: actions/checkout@v6
      - name: MCP config
        run: ... (profil ci-spec : spec-draft, spec-lint, memory-recall, codebase-ask)
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_federation_rule_id: fdrl_xxxxxxxx
          anthropic_organization_id: 00000000-0000-0000-0000-000000000000
          prompt: |
            Issue #${{ github.event.issue.number }}.
            execute : spec.draft(brief = corps de l'issue) puis spec.lint(handle).
            Si lint échoue, spec.revise une fois. Ouvre une PR avec le markdown sous decisions/.
          claude_args: |
            --mcp-config /tmp/mcp.json
            --allowedTools mcp__gateway__search,mcp__gateway__describe,mcp__gateway__execute

Un second workflow, sans Claude, exécute spec-lint comme check obligatoire sur toute PR touchant decisions/.

7.5 platform-build.yml, stage 0 et porte de tests (sans Claude)

name: platform-build
on:
  push: { branches: [main] }
  pull_request:

jobs:
  build:
    runs-on: [self-hosted, platform]
    container: ghcr.io/cdeust/stage0:current      # image figée, promue seulement par ce workflow
    steps:
      - uses: actions/checkout@v6
      - run: make build test                         # vN+1 construite par stage0
      - run: ./stage0/fixpoint.sh                    # vN+1 reconstruit vN+1 ; porte de tests (attendu = base + ajoutés − supprimés, tous verts)
      - if: github.ref == 'refs/heads/main' && success()
        run: ./stage0/promote.sh                     # stage0:current ← vN+1

La seule porte de merge est le résultat des tests : nombre attendu = tests de la base + ajoutés − supprimés (exemple : 6445 + 30 − 10 = 6465), ajouts et suppressions dérivés du diff de la PR, pas déclarés. Le nombre exécuté doit égaler le nombre attendu et tous les tests doivent être verts, sinon pas de merge. Si la porte échoue, stage0:current ne bouge pas et la CI reste capable de reconstruire la plateforme. C'est la réponse au problème de bootstrap.

7.6 Runner auto-hébergé

  • Un runner par environnement, étiqueté platform, dans le même segment réseau que la gateway. Aucun accès sortant autre que GitHub et la gateway.
  • Le runner n'a pas Docker exposé à Claude. Les conteneurs sont ceux de la plateforme.
  • Le runner est jetable : image reconstruite par platform-build, pas de state entre deux jobs.
  • Tous les workflows tournent depuis la branche par défaut (pull_request, pas pull_request_target sauf pour agent-approval-check, qui est conçu pour).

9. Décisions ouvertes

  • Support de l'extension tasks par Claude Code, Codex et claude-code-action : à tester en brique 2 ; task.wait reste tant que ce n'est pas confirmé.
  • Jev : déploiement EU ou on-prem à obtenir par écrit ; sans réponse, Judge local sur toute donnée sensible.
  • Serveurs on-prem Mac ou Linux pour le Structurer : recommandation open-weight contraint, pour garder un seul compose.
  • Transport HTTP de la gateway dans --mcp-config : vérifier la syntaxe exacte attendue par la version de Claude Code installée par l'action au moment de la brique 2.
