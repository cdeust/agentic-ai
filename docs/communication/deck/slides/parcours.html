Le parcours d’un appel « execute »

1

client → gateway

execute(script), l’un des trois méta-tools

2

gateway

Ouvre la task avec ses bornes, lance l’executor sous srt

3

executor → gateway → module

Le script appelle un outil ; la gateway vérifie les droits

4

executor

Le script filtre et agrège ; les étapes 3 et 4 se répètent

5

gateway → verify, registre

Si du code est produit, verify le valide ; tout va au registre

6

gateway → client

Un résultat borné, sinon un résumé et un handle

Seul le résultat de la dernière étape entre dans le contexte du client.

Suivons un appel du début à la fin. Le document le décrit en douze étapes ; je les ramène à six. Un, le client appelle execute avec un script. Deux, la gateway vérifie l’accès et le profil du client, ouvre une task avec ses bornes, c’est-à-dire un délai maximal et un nombre maximal d’appels, puis lance l’executor sous srt. Le script n’est jamais passé en argument de ligne de commande : l’executor le récupère ensuite par le canal MCP. Trois, le script appelle un outil, par exemple le rappel de mémoire. La gateway vérifie que cet appel est permis, contrôle la profondeur, crée un identifiant d’appel à usage unique et transmet au module, qui s’exécute lui aussi sous srt. Quatre, le script filtre et agrège ; les étapes trois et quatre se répètent autant que nécessaire. Cinq, si du code a été produit, verify le valide, et la gateway écrit au registre la trace, le verdict et les tokens consommés. Six, le client reçoit un résultat borné ; s’il est trop long, un résumé déterministe et un handle pour aller chercher le reste. Le point à retenir : seul ce dernier résultat entre dans le contexte du client. Le document le marque comme à prouver, par un scénario prévu à la brique 3. On ne l’affirme donc pas encore comme acquis.
