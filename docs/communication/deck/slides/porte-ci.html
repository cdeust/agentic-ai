Troisième problème : la CI. Une version précédente voulait prouver que deux builds produisaient les mêmes empreintes. La conception actuelle retire cette idée : seul le résultat des tests fait foi, aucun hash, aucun digest. Il y a trois familles de tests. Les tests de bout en bout et les tests unitaires sont écrits en Gherkin, une syntaxe Given, When, Then que l’on peut lire sans être développeur ; les tests de bout en bout tournent avec srt et Postgres réels. La troisième famille est la mutation, avec Stryker : l’outil modifie volontairement le code, par exemple il inverse une condition, et vérifie qu’au moins un test échoue. Un mutant qui survit, c’est un test qui ne vérifie rien. La règle : zéro survivant sur les lignes modifiées. Enfin le compte. Le nombre de scénarios exécutés doit égaler la base, plus les ajoutés, moins les supprimés. La porte est verte si et seulement si chaque scénario attendu a tourné, en une seule tentative, avec chaque step au statut PASSED. Pourquoi si strict : le banc a montré, test T-13, qu’un step sauté donnait quand même success: true et un code de sortie 0. Un test sauté ressemblait à un test réussi. La porte lit donc le rapport détaillé, jamais le code de sortie. C’est la preuve par l’expérience appliquée à notre propre outillage. Cette porte s’écrit à la brique 1a.
